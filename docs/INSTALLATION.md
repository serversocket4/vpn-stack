# Установка на свои серверы

## Границы установщика

Комплект состоит из исходников работающих компонентов и инструментов подготовки новой установки. Полный запуск опубликованного варианта на двух чистых VPS пока не проверен. Нужен оператор, который понимает Linux, systemd, SSH и firewall.

`prepare.py` создаёт конфигурации и новые секреты в отдельной приватной папке. `install.py` проверяет свежие целевые пути, копирует файлы и подготавливает Python-окружение. Он не устанавливает внешние VPN-ядра и не включает службы автоматически. `relay.py` генерирует файлы пересылки RU, но сам их не применяет.

Не направляйте установщик на действующий сервер с чужими сервисами без отдельной проверки портов и конфигураций. Для первой установки используйте отдельные VPS.

## 1. Подготовьте окружение

Целевая схема: Linux с systemd на обоих VPS, IPv4 RU и NL, root-доступ по SSH. Рекомендуемая базовая ОС — Ubuntu 24.04. Python должен поддерживать аннотации `X | None` — не ниже 3.10.

На NL понадобятся:

- Xray с поддержкой используемой конфигурации XHTTP/REALITY и командой `x25519`;
- Hysteria2 с obfuscation Salamander;
- Telemt для MTProto-прокси;
- Caddy;
- Python, venv, pip, `aiohttp` и `PyYAML`;
- `openssl`, `curl`, `qrencode`, `iproute2`, `ping`, `flock`, SSH-клиент и polkit.

На RU нужны `nftables`, systemd, Python, `iproute2` и OpenSSH. Подготовьте сетевой доступ NL → RU для управления и проверок.

Backend и его systemd units используют системный `/usr/bin/python3`. Модуль `yaml` должен быть доступен именно этому интерпретатору; установки PyYAML только в venv админки недостаточно. В Ubuntu для системного Python предусмотрен пакет `python3-yaml`.

Внешние программы устанавливайте из их официальных проектов. Подбирайте совместимые версии, проверяйте опубликованные контрольные суммы и сохраняйте выбранные версии в своей документации. Бинарные файлы сторонних проектов в этот репозиторий не входят; ссылки приведены в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).

Официальные пакеты и установщики часто создают свои конфиги и systemd units, например `Caddyfile` и `caddy.service`. Установщик VPN Stack откажется перезаписывать даже такие штатные файлы. В этом случае нужна ручная интеграция: сравните конфигурации, сохраните исходные файлы и решите, какие units будут использоваться. Не удаляйте файлы чужого установщика автоматически ради прохождения проверки. Вариант установки только совместимых бинарников также требует проверки целевых путей.

Скрипт `bvpn-health` также проверяет службы `fail2ban`, `ufw` и `unattended-upgrades`. Установите и настройте их, если используете этот health-check без правок; иначе приведите список проверок в соответствие со своей системой до включения таймера.

## 2. Создайте собственного бота

Создайте бота через [BotFather](https://t.me/BotFather), получите его токен и отправьте новому боту `/start` со своего Telegram-аккаунта. Укажите числовой chat ID своего чата. Не используйте бота и идентификаторы другой установки.

Токен и chat ID записываются в приватный файл параметров, из которого генератор создаст `/etc/bvpn-admin/env`. В сервисном env используются `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `OWNER_EMAIL` и `PUBLIC_URL`.

Узнать chat ID можно из входящего обновления Bot API методом `getUpdates`, пока бот ещё не запущен в другом процессе. Не публикуйте полный ответ API и не вставляйте токен в команды, которые попадут в историю терминала. Официальное описание метода: [Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

## 3. Подготовьте TLS

Для HTTPS-страниц и VLESS TCP/TLS нужен действующий сертификат, покрывающий **публичный IP NL**, и соответствующий приватный ключ. Генератор получает их через `--site-cert` и `--site-key`. Это не имена файлов, уже поставляемых проектом.

Шаблон Caddy использует предоставленные статические сертификаты. Получение, продление и доставка обновлённого сертификата остаются задачей владельца установки. Факт наличия Caddy сам по себе не означает, что сертификат из такого шаблона будет продлеваться.

Существующий `bin/bvpn-tls-sync` предназначен для другого режима: он ищет управляемый Caddy сертификат IP в хранилище Caddy. Не включайте `bvpn-tls-sync.timer` для статического сертификата, рассчитывая на автоматическое продление. При замене сертификата обновите все использующие его конфигурации, проверьте их и перезагрузите соответствующие службы. Если отдельно меняется сертификат Hysteria, обновите его pin в клиентских профилях и подписках.

## 4. Создайте приватные конфигурации NL

Склонируйте репозиторий на машину подготовки с установленными `xray` и `openssl`:

```sh
git clone https://github.com/OWNER/vpn-stack.git
cd vpn-stack
umask 077
cp examples/installation.json /root/vpn-stack-settings.json
chmod 600 /root/vpn-stack-settings.json
```

Заполните приватный JSON по примеру: IP NL, IP RU, имя установки, идентификатор владельца админки, собственный токен бота и chat ID. Адреса из примера демонстрационные. Если меняете REALITY server name, проверьте доступность соответствующего TLS-назначения с NL.

```sh
python3 scripts/prepare.py \
  --settings /root/vpn-stack-settings.json \
  --output /root/vpn-stack-runtime \
  --site-cert /защищённый/путь/site.crt \
  --site-key /защищённый/путь/site.key
```

Генератор создаёт собственные UUID, ключи REALITY, доступы Hysteria/Telemt и комплекты `owner` и `monitoring`. Никакие доступы другой установки не переносятся. Начальная маршрутизация берётся из `examples/routing.json`; просмотрите её доменные группы и источники геобаз перед генерацией и проверьте загрузку правил в своём клиенте.

Содержимое runtime включает секреты: держите его вне Git и публичной папки, с правами только для администратора. До установки просмотрите сформированные конфигурации и службы. Проверьте Xray установленным ядром и Caddy командой `caddy validate` с соответствующим путём к конфигурации.

## 5. Установите файлы NL

Сначала выполните проверку без применения:

```sh
sudo python3 scripts/install.py --runtime /root/vpn-stack-runtime --dry-run
```

На новом выделенном NL-сервере после проверки:

```sh
sudo python3 scripts/install.py --runtime /root/vpn-stack-runtime
```

Не обходите отказ при обнаружении существующих файлов. Проверьте, какие файлы уже занимают пути, и выберите отдельный VPS либо проведите ручную интеграцию.

Основные пути установки:

| Путь | Назначение |
| --- | --- |
| `/opt/bvpn-admin/` | Админка и её Python-окружение |
| `/usr/local/lib/bvpn/` | Backend и сервер подписок |
| `/usr/local/sbin/bvpn*` | Привилегированные команды |
| `/etc/bvpn/` | Идентичность сервера и настройки VPN |
| `/etc/bvpn-admin/env` | Секреты бота и адрес админки |
| `/var/lib/bvpn-admin/` | Приватные БД админки и мониторинга |
| `/var/lib/bvpn-sub/` | Подписки и метаданные |

## 6. Подготовьте RU

Сгенерируйте файлы пересылки, подставив настоящий адрес NL:

```sh
python3 scripts/relay.py \
  --nl-ip NL_IP \
  --output /root/vpn-stack-relay \
  --xhttp-port 18443
```

`NL_IP` в примере — обозначение, его нужно заменить своим IPv4. Генератор создаёт файлы для отдельных таблиц nftables и собственной службы. Перед ручной установкой просмотрите результат, проверьте `nft --check` и занятость портов. Не добавляйте глобальное `flush ruleset` и не заменяйте firewall других приложений.

Для прохождения пакетов нужен `net.ipv4.ip_forward=1`; подготовленная служба пересылки должна включать его при запуске. Firewall и провайдер должны пропускать выбранные TCP/UDP-порты. Удалённые правила доступа провайдера не меняются этими скриптами.

Отдельно подготовьте SSH для управления **с NL на RU**. Backend сначала обращается к TCP 2222. Если провайдер NL запрещает исходящий TCP 22, одного стандартного SSH-входа RU недостаточно. Дополнительный SSH-вход на 2222 создаётся вручную: проверьте его конфигурацию, ограничьте доступ адресом NL, добавьте собственный служебный ключ и закрепите проверенный host key. Сохраните независимый вход владельца через обычный SSH или консоль провайдера.

Backend ожидает конкретные пути на **NL**:

- приватный ключ — `/root/.ssh/id_ed25519_vpn_relay`;
- публичный ключ — `/root/.ssh/id_ed25519_vpn_relay.pub`;
- проверенные ключи хостов — `/etc/bvpn/relay_known_hosts`.

На новой NL-установке создайте каталог SSH и отдельный служебный ключ. Ключ без парольной фразы нужен для фонового systemd-задания; приватный файл остаётся доступен только root. Если ключ по этому пути уже существует, сначала выясните его назначение и не перезаписывайте его.

```sh
umask 077
install -d -m 700 /root/.ssh
python3 - <<'PY'
from pathlib import Path
import subprocess

key = Path('/root/.ssh/id_ed25519_vpn_relay')
if key.exists() or key.with_suffix('.pub').exists():
    raise SystemExit('Ключ уже существует: проверьте его вручную, замена не выполнена')
subprocess.run(['ssh-keygen', '-q', '-t', 'ed25519', '-N', '',
                '-C', 'vpn-stack-relay', '-f', str(key)], check=True)
key.chmod(0o600)
PY
```

Через доверенную консоль RU добавьте **только публичный** файл этого ключа в `/root/.ssh/authorized_keys`, сохраняя остальные разрешённые ключи. Каталог `.ssh` на RU должен принадлежать root и иметь права `0700`, файл `authorized_keys` — `0600`. Приватный ключ с NL на RU не копируют.

До первого SSH-подключения получите публичный host key RU через консоль провайдера: `/etc/ssh/ssh_host_ed25519_key.pub`. Там же посмотрите его SHA256-отпечаток командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256`. Передайте публичный файл на NL доверенным способом, например как `/root/ru-host-ed25519.pub`, и сравните отпечаток:

```sh
ssh-keygen -lf /root/ru-host-ed25519.pub -E sha256
```

Только после совпадения с отпечатком из консоли запишите ключ в отдельный known_hosts. Этот пример берёт IP RU из созданного конфигурационного файла, не перезаписывает существующий known_hosts и добавляет alias `[RU_IP]:2222`, который нужен SSH для нестандартного порта:

```sh
python3 - <<'PY'
from pathlib import Path
import ipaddress
import json

relay = str(ipaddress.IPv4Address(json.loads(
    Path('/etc/bvpn/relay.json').read_text())['ip']))
fields = Path('/root/ru-host-ed25519.pub').read_text().split()
if len(fields) < 2 or fields[0] != 'ssh-ed25519':
    raise SystemExit('Ожидается проверенный публичный Ed25519 host key RU')
host_key = ' '.join(fields[:2])
known = Path('/etc/bvpn/relay_known_hosts')
with known.open('x') as target:
    target.write(f'{relay} {host_key}\n[{relay}]:2222 {host_key}\n')
known.chmod(0o600)
PY
```

Если known_hosts уже существует, проверьте его вручную и добавьте подтверждённую запись без удаления остальных хостов. `ssh-keyscan` сам по себе не подтверждает подлинность ключа.

Проверьте фоновый вход с NL, заменив `RU_IP` настоящим адресом своего RU:

```sh
ssh -p 2222 -i /root/.ssh/id_ed25519_vpn_relay \
  -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o UserKnownHostsFile=/etc/bvpn/relay_known_hosts root@RU_IP true
```

Команда должна завершиться успешно без запроса пароля и без ослабления проверки host key. После этого сборщик сможет читать метрики RU и запускать межсерверные проверки.

## 7. Проверьте и запустите

После проверки файлов загрузите units через `systemctl daemon-reload`. Включайте только те службы, для которых действительно установлены программы и заполнены конфигурации: Xray, Hysteria, Telemt, Caddy, `bvpn-sub`, `bvpn-admin`, затем таймеры мониторинга и снимков. Установщик за вас их не запускает. Для статического TLS не включайте таймер синхронизации сертификата, описанный выше.

Проверьте доступность локальной админки за Caddy, страницы подписок по HTTPS и каждого публичного VPN-порта. Затем используйте:

```sh
sudo /usr/local/sbin/bvpn selftest
sudo python3 /usr/local/lib/bvpn/monitor_collect.py --dry-run
sudo python3 /usr/local/lib/bvpn/monitor_collect.py --once --no-write
```

Сухой план показывает параметры проверок. Последняя команда запускает реальные временные VPN-клиенты, но не записывает снимок мониторинга.

Отправьте своему боту `/password`, задайте пароль через одноразовую ссылку и войдите в админку с подтверждением в боте. Дождитесь первого снимка пользователей или обновите снимок через админку: он нужен для публикации подписки. Затем создайте подписку, импортируйте её на тестовое устройство и проверьте реальный доступ, DNS, видео и звонки. Серверная самопроверка не заменяет проверку из Wi-Fi и мобильной сети.

Сохраните защищённую копию своих конфигураций, БД и ключей вне обоих VPS. В репозиторий их не добавляют.
